Case study · Infrastructure governance

Read-Only Infrastructure Audit Pipeline

I built a read-only audit workflow that separated sensitive collection records from sanitized reports, documented every remote command and surfaced uncertainty rather than filling gaps with guesses.

Context

A mixed infrastructure estate needed a current inventory of operating systems, services and component versions. The collection method had to be safe enough for production and the resulting report had to be useful without exposing the estate itself.

Problem

Infrastructure discovery can become risky when scripts write files, restart services, read secret-bearing configuration or turn raw command output into a broadly shared document. Access gaps create a second problem: an audit can look complete while silently omitting systems it could not reach.

Constraints

  • Remote execution had to remain read-only.
  • Some systems were inaccessible or could not expose a version safely.
  • Raw output and structured inventory contained employer-sensitive detail.
  • Shareable DOCX, PDF and CSV artifacts needed separate privacy review.

Architecture

The workflow used a documented scope and remote-command manifest, a collector that produced timestamped records, separate raw and sanitized stores, structured CSV/JSON inventory and generated stakeholder reports. Owner-confirmation items remained visible rather than being converted into assumptions.

Investigation

I classified what each component could reveal through safe commands, what required sensitive configuration and what could not be confirmed with the available access. That shaped both the command allowlist and the report’s limitation model.

Implementation

I authored the audit scope, command manifest, collector, inventory model, report builder and share-safety review. The report pipeline kept sensitive collection records local, generated sanitized outputs and provided a concise update for non-specialist stakeholders.

Change-safety controls

The command manifest excluded restarts, reloads, package changes, file writes, deletes, permission changes, database mutations and container lifecycle commands. New commands could not be added informally; they had to remain read-only and documented.

Validation

Shareable Markdown, DOCX, PDF, CSV and sanitized records were scanned for secrets and sensitive patterns. The command manifest was reviewed independently for state-changing verbs, and access-limited systems remained marked for owner confirmation.

Rollback strategy

The audit’s safest rollback was prevention: no production state was intentionally changed. Generated reports could be rebuilt from the retained local records without repeating remote collection.

Outcome

The workflow produced a structured, reviewable inventory and stakeholder report while preserving uncertainty, access failures and sensitive raw collection records in the correct boundary.

Technologies

Linux, shell automation, structured CSV/JSON inventory, Markdown, DOCX/PDF generation, secret scanning and report sanitization.

Public/private boundary

No live inventory, server aliases, versions, topology, addresses, access paths or secret-bearing configuration is published.
