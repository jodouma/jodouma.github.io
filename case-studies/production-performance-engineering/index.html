Performance engineering

Engineering Reliability Across 80M+ Monthly Requests

I engineered capacity continuously across Cloudflare, Nginx, Passenger, Rails, PostgreSQL, Redis, queues, pools, memory and caching for more than 80 million monthly requests across 12 production domains.

Context

An international Rails marketplace handled more than 80 million requests per month across 12 production domains. The same customer request could cross Cloudflare, Nginx, Passenger, Rails, PostgreSQL or Redis while competing with background work, crawler traffic and finite host resources.

Problem

The platform could appear underprovisioned when the real problem was misaligned concurrency. Adding Passenger processes might increase PostgreSQL connections and memory; enlarging a queue might postpone rejection while making recovery worse; tuning the database alone might leave an overloaded application pool unchanged. Performance had to be engineered as a continuous system, not a one-time configuration tweak.

Architecture

Requests move from the edge into Nginx, through the Passenger-managed Rails runtime and toward PostgreSQL or Redis. Application monitoring, host metrics and logs make each boundary inspectable so the constrained layer can be isolated before tuning.

Investigation

I correlated New Relic application behavior with Nginx/Passenger queues, process lifecycle, memory and CPU, PostgreSQL activity and connections, Redis health, background workers, host storage and Cloudflare delivery. During one scaling experiment, adding processes drove the waiting queue beyond 1,900 instead of increasing useful throughput—a clear signal that the shared downstream boundary, not the worker count, was controlling capacity.

Responsibilities

I owned production investigation and capacity decisions across those boundaries: pool and queue sizing, connection alignment, process recycling, stable sockets, server upgrades and rebuilds, caching policy, database/storage work, alert thresholds, controlled experiments and recovery paths.

Technical approach

  • Observe the request path and resource signals before selecting a change.
  • Distinguish edge, proxy, runtime, application, database, cache, worker and host constraints.
  • Align Passenger, Rails and PostgreSQL pools rather than maximize each component independently.
  • Cap queues and alert on saturation so overload remains visible and bounded.
  • Validate downstream connection, memory and dependency pressure after every experiment.
  • Convert the accepted state into monitoring, documentation and a rollback-ready configuration.

Validation

Validation compared queue depth, process state, database connections, memory, response behavior and dependency health before and after a change. I exercised representative application paths and retained the prior configuration until the wider system—not only the edited service—showed a safe result. The production scale remains 80M+ monthly requests across 12 domains; short monitoring windows are not extrapolated into a second monthly metric.

Outcome

Capacity engineering became a continuous operating practice across the full request path. Saturation became more observable, interventions became narrower, and the team gained a repeatable way to decide whether a symptom required edge policy, runtime tuning, data work, cache recovery, host change or application collaboration.

Technologies
