Production engineering case study

Migrating 12 Production Domains Behind Cloudflare

I migrated and integrated Cloudflare across 12 production domains, centralizing DNS, edge security, TLS/DNS-01 lifecycle, crawler access and domain monitoring through staged validation and rollback.

Context

An international marketplace operated 12 localized production domains on a shared application platform. Each domain carried independent DNS, certificate, crawler and reputation risk; a mistake could remove a market from service or search even when the origin application itself remained healthy.

Problem

The program needed to centralize edge and domain control without creating a 12-domain blast radius. DNS cutover, visitor-to-edge and edge-to-origin encryption, dynamic routes, assets, timeouts, crawler trust and origin protection all required different checks. Certificate automation also had to stop depending on a renewal path that could interfere with the Rails/Passenger tier.

Constraints

  • Live traffic could not be treated as a disposable test environment.
  • Dynamic and long-running application paths behaved differently from static assets.
  • A DNS-only workaround could restore reachability while exposing the origin to direct traffic.
  • Legitimate search and AI crawler access had to survive security policy changes.

Architecture

The public architecture is deliberately generic: clients connect to a managed edge, which handles TLS and forwards compatible traffic to the origin web tier. Static and dynamic paths receive different delivery treatment, while DNS, certificate and origin controls provide the operational boundary around the application.

Investigation

I first mapped each domain's records, certificate state, application behavior, crawler access and dependencies. I separated the program into control areas: encryption and redirects, DNS-01 validation, protocol and compression behavior, static versus dynamic delivery, application-specific timeouts, proxy state, origin exposure and external domain health. A recurring Passenger/certificate incident reinforced why renewal and application runtime had to be decoupled.

Implementation

I migrated the estate domain by domain, preserving the previous state and rollback path before each cutover. I established full-path TLS/HTTPS behavior, moved issuance and renewal to Cloudflare DNS-01 where appropriate, enabled delivery controls conservatively, and connected domain/certificate checks to alerting. The operating model then expanded into crawler identity, suspicious traffic, cache policy and origin-protection decisions across all 12 domains.

Change-safety controls

Every domain was a production change. I recorded DNS/proxy state, checked resolution and HTTPS, exercised representative application paths, checked legitimate crawler responses and watched edge/origin behavior before widening the rollout. DNS-only routing remained an exceptional recovery option because it could expose the origin.

Validation

Validation covered DNS resolution, HTTPS reachability, certificate trust/expiry, protocol compatibility, dynamic and static paths, crawler access, origin protection and reversible proxy state. External domain checks kept renewal, expiry, reachability and blacklist/reputation risk visible after migration rather than treating cutover as the finish line.

Rollback strategy

The rollback model preserved the last known DNS and proxy state per domain and required the same resolution, TLS, application and crawler checks after reversal. This kept a problem in one market from becoming a rushed estate-wide change.

Outcome

All 12 production domains moved behind a centralized Cloudflare operating model spanning DNS, TLS, edge security, monitoring and crawler visibility. Domain lifecycle became an observable platform responsibility rather than a collection of one-off provider settings.

Technologies

Cloudflare, DNS, TLS, DNS-01 automation, HTTPS, HTTP/2 and HTTP/3 concepts, Brotli, cache policy, Nginx-facing edge operations, suspicious-traffic analysis and production validation.
