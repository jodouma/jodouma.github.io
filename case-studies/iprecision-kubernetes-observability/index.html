Case study · AWS, Kubernetes and observability

AWS EKS Delivery, Observability and Anomaly Detection

I designed and implemented an AWS EKS delivery and observability environment, then used Metricbeat and Kibana anomaly detection to observe behavior during a controlled DDoS-style load test.

Context

At iPrécision, my approved scope connected cloud infrastructure, delivery automation, container orchestration and observability. The goal was to turn a source change into a deployed workload and make the resulting environment understandable through logs and system telemetry.

Problem

Delivery and monitoring were often discussed as separate exercises. This implementation joined them: build and test a container, deploy it to Kubernetes, collect operational signals and use those signals to investigate abnormal behavior.

Constraints

  • This was a substantial applied cloud environment, not enterprise production tenure.
  • The wider project was collaborative; my attribution covers the principal cloud, delivery and observability components in my documented scope.
  • Several telemetry paths were evaluated before the final demonstrated approach.
  • A controlled load test cannot be represented as a real production attack or business incident.

Architecture

Source changes triggered a Jenkins workflow that built and tested a Docker image. The image fed an Amazon EKS deployment managed through Kubernetes resources. Helm-installed Elastic components and Metricbeat collected node, container, process and network signals into Kibana dashboards and anomaly-detection jobs.

Investigation

I evaluated CloudWatch/OpenSearch and Elastic-oriented telemetry paths before documenting the Kubernetes-native Metricbeat and Kibana implementation. Dashboards established normal operating context before anomaly jobs were used to examine deviations.

Implementation

My scope included the AWS environment, Jenkins/Docker delivery flow, EKS cluster and workload deployment, Helm-based Elastic services, Metricbeat collection, dashboards and anomaly-detection configuration. The implementation documented running pods and services, application access and populated operational dashboards.

Change-safety controls

Pipeline stages separated build, test and delivery. Cluster and telemetry state were checked after deployment rather than treating a successful command as proof that the environment worked. Private keys, endpoints and account material remain outside the public story.

Validation

Validation covered the Jenkins stages, container creation, Kubernetes pod/service state, application exposure, Metricbeat ingestion and Kibana dashboards. A controlled DDoS-style load test then produced visible traffic and resource changes plus log and processor anomaly signals.

Rollback strategy

The archived report records deployment iteration and validation, but it does not prove a formal enterprise rollback program. I therefore discuss recovery-oriented verification and Kubernetes deployment controls without claiming an unmeasured recovery result.

Outcome

The environment demonstrated an automated delivery path, EKS/Kubernetes deployment, centralized operational telemetry and anomaly detection under controlled load. The anomaly models supported observation and investigation; they did not themselves stop traffic.

Technologies

AWS EC2 and EKS, Kubernetes, Docker, Jenkins, GitHub webhooks, Helm, Elasticsearch, Kibana, Metricbeat, CloudWatch/OpenSearch evaluation and CI/CD.
