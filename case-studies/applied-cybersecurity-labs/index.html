Case study · Security education

Applied Cybersecurity and CTF Laboratories

I designed and delivered two isolated laboratories that connected offensive investigation with defensive architecture, repeatable setup, validation, teardown and explicit authorized-use boundaries.

Context

Cybersecurity students needed practical environments where infrastructure and application weaknesses could be investigated safely. The aim was not to reward memorized commands; it was to connect observation, documented findings and mitigation.

Problem

A useful lab must feel realistic without targeting a real system, leaking student data or publishing a reusable unsafe deployment. It also needs deterministic setup so each learner starts from a known state and instructors can distinguish investigation from guesswork.

Constraints

  • Vulnerabilities were intentional and restricted to isolated training environments.
  • Credentials and exact exploit paths could not become public portfolio content.
  • Student identities, grades, messages and outcomes remained private.
  • Environments needed repeatable setup, reset, validation and teardown.

Architecture

The first lab used a restricted AWS/Linux environment with staged reconnaissance, access and privilege-analysis objectives. The second used a Flask application with PostgreSQL, deterministic data and intentionally vulnerable authentication, authorization and data-access behavior. A split app/database model added infrastructure and network reasoning.

Investigation

Each lab asked learners to move from surface observation toward a documented finding: identify exposed services or application behavior, determine why a boundary failed, confirm what access became possible and relate the result to a safer configuration or code path.

Implementation

I designed the objectives, environment, staged progression, instructor checks and safety notes. Supporting automation covered provisioning or bootstrap, deterministic seed data, validation scripts, reset paths and teardown. Instructor material separated expected findings from hints and ethical boundaries.

Change-safety controls

The labs were explicitly authorized-use environments. Network access was constrained, destructive persistence was unnecessary, and reset/teardown procedures prevented a training state from becoming a forgotten exposed service.

Validation

Known flags or observable application states provided deterministic checkpoints. Setup and health checks confirmed prerequisites, while teardown and reset paths returned the environment to a controlled baseline.

Rollback strategy

Infrastructure was disposable or resettable by design. The public case study describes that lifecycle without publishing deployable vulnerable defaults or credentials.

Outcome

The two labs created reusable paths through AWS/Linux investigation and Flask/PostgreSQL application security. No student count, score, placement or learning-outcome metric is claimed.

Technologies

AWS EC2, CloudFormation, Linux, Nginx concepts, network investigation, Flask, PostgreSQL, Python automation, deterministic fixtures and validation scripts.

Public/private boundary

No student identity, real target, endpoint, credential, exploit chain, private message or unsafe deployment template is published.
